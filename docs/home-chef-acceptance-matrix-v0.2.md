**版本：** v0.2（草案）

## 1. 规则与证据

每项验收记录应包含：`AC-ID`、来源需求 ID、优先级、场景类型、前置条件、操作步骤、预期页面/状态/金额/通知/日志、证据、执行人、状态、缺陷或豁免。验收矩阵只验证既有规则，不得创建未在 `PRD/TR/COMP/OPS/NFR` 定义的新业务规则。

P0 未通过或未获正式豁免不得上线；豁免必须有风险、临时控制、到期日和产品/技术/合规责任人。测试环境需提供用户、认证厨师、过期厨师、不同档期、支付/退款沙箱、可推进时钟和后台角色账号。

## 2. 基础产品能力验收

每个 `AC-*` 是**验收场景定义**；执行时必须在同名验收记录中补全并保存下列字段，缺任一字段不得标记为通过：

| 字段 | 执行时必须填写 |
|---|---|
| 优先级与场景类型 | P0/P1/P2；正常、异常或边界 |
| 前置条件 | 账号角色、订单/支付/规则版本、模拟时间、测试数据 |
| 操作步骤 | 可复现的编号步骤，含调用端或后台角色 |
| 预期结果 | 页面、全部受影响状态域、金额、通知、审计日志 |
| 实际结果与证据 | 截图、渠道流水、审计事件、日志查询或演练纪要链接 |
| 执行信息 | 执行人、环境、日期、通过/失败/豁免、缺陷或豁免单号 |

## 4. 状态、并发与金额验收

`AC-STATE-001`：对交易规则第 3.1 节七个状态域的每个合法转换至少验证一次；每个非法转换（未支付开始服务、未结清结算、已关闭重新支付等）必须被服务端拒绝并留痕。支付成功但硬锁失败、退款失败重试、服务中止/爽约后的跨域终态由 `AC-TR-016`、`AC-TR-013`、`AC-TR-008` 补充验收。

`AC-CONSIST-001`：重复点击、重复支付回调、退款回调乱序、补款失败重试、厨师多设备报价、用户与系统同时取消均不得重复金额或产生矛盾状态。

`AC-MONEY-001`：核算 TR-COMMISSION-001、TR-COMMISSION-002 的 E1–E4、E8–E9（无券、示例15%），并验证不同等级/业务费率快照；E5–E7待必要参数发布后填写具体输入与期望，不以“按规则”标记通过。核对净实收、待补/待退与佣金，优惠样例按AC-TR-019另计。

`AC-SCHEDULE-001`：自选付款时锁指定厨师、匹配抢单时唯一绑定并锁档；报价失效、取消、改期、履约结束按规则释放。重复抢单、两个订单争同档、超时竞态不重复硬锁，候选未绑定不占他人档期。

## 8. 追踪、退出与上线门禁

P0/P1产品、交易、合规、运营和NFR ID须至少关联一个验收项；资金规则覆盖正常与边界，角色覆盖正向与越权。新增的 `AC-PRD-018`～`AC-PRD-024`、`AC-TR-017`～`AC-TR-020`、`AC-OPS-005`～`AC-OPS-008`、`AC-COMP-005`、`AC-NFR-009`～`AC-NFR-010` 也属于追踪范围。`OPS-CONTENT-001` 由 `AC-PRD-020` 与 `AC-COMP-005` 覆盖；`TR-DEPOSIT-001` 是明确的 MVP 排除项，按范围门禁核验“不建设履约保证金能力”，不创建虚假的资金功能验收。第5、6节是合规/运营与NFR场景定义，缺实际执行证据不得标记通过。对齐记录的DTL参数未发布时，依赖场景标为待执行；文档追踪通过不等于上线验收通过。

上线前必须关闭或正式豁免：`BLK-REGION-001`、`BLK-ENTITY-001`、`BLK-PAY-001`、`BLK-CHEF-HEALTH-001`、`BLK-SETTLE-001`、`BLK-FOOD-001`、`BLK-RETENTION-001`。产品、技术、运营、财务、合规共同签署 Go/No-Go 结论；任何未关闭 P0 阻断项均为 No-Go。
