# 厨师结算、微信提现与微信直接分账

代码已接入，真实商户权限及配置尚缺，因此不会向真实微信账户出款。当前自动化测试使用隔离数据库和测试签名响应，不代表已完成微信真机验收。

## 两条资金路径

| 路径 | 资金处理 | 厨师操作 |
| --- | --- | --- |
| 余额结算 + 微信商家转账（默认） | 用户付款 → 完成服务及费用确认 → 售后保护期结束 → 财务按订单快照分配佣金与厨师收入 → 计入可提现余额 → 提现审核 → 微信确认到账 | 小程序“我的 → 进入接单工作台 → 我的收入”，绑定微信实名资料、申请提现、确认收款 |
| 微信直接分账（选配） | 用户订单按分账标记支付 → 完成确认及保护期 → 财务结算 → 添加个人 OpenID 接收方 → 微信分账 → 查询确认到账，剩余金额解冻给平台 | 先绑定实名收款资料，然后查看分账到账记录；这部分不再进入可提现余额 |

每笔订单在第一次预支付时锁定资金路径，后续定金/尾款沿用该路径。切换配置不追溯修改历史订单，直接分账和提现不会重复支付同一份收入。

默认结算保护期为确认服务完成后的 168 小时，与现有普通售后窗口一致；可延长至最多 720 小时。已完成、费用结清、无欠款、无未完成退款和争议的订单才可结算。部分履约裁定订单不按普通佣金直接结算，需要单独处理资金分配。

佣金取订单规则快照：`佣金 = round(人工服务费 × 佣金率)`；`厨师收入 = 净实收 + 平台优惠补贴 - 佣金`。例如人工服务费 98 元、15% 佣金、无补贴和食材费，厨师应得 83.30 元，平台佣金 14.70 元。佣金率调整不改变历史订单。

余额分配以不可修改的 ChefWalletEntry 记录。申请提现先冻结金额；并发申请不能超出余额，重复请求不重复冻结。拒绝申请、用户取消尚未审批的申请、微信明确返回 FAIL/CANCELLED，均以一笔冲正流水退回余额。网络超时或不明状态不会释放余额，不会另造转账单。

## 商户权限和配置

先完成 [用户支付配置](wechat-pay.md)。在此基础上：

### 微信商家转账

在微信支付商户平台申请适合实际厨师服务收入的商家转账场景，使用获批的场景 ID 和报备字段。普通小程序支付开通不等于已有转账权限。

```dotenv
CHEF_SETTLEMENT_HOLD_HOURS=168
WECHAT_TRANSFER_ENABLED=false
WECHAT_TRANSFER_SCENE_ID=
WECHAT_TRANSFER_SCENE_REPORTS='[]'
WECHAT_TRANSFER_MAX_FEN=200000
```

`WECHAT_TRANSFER_SCENE_REPORTS` 是真实场景要求的 JSON 数组，例如每项包含 `info_type` 和 `info_content`。不同场景要求不同，不能照抄营销红包场景的样例。这里不预填虚构的获批场景。`WECHAT_TRANSFER_MAX_FEN` 是平台单次提现上限，单位分，还要满足商户自己的微信额度。

配置就绪后开启 `WECHAT_TRANSFER_ENABLED=true` 并重启 API。继续使用用户支付的商户号、AppID、商户私钥和微信公钥。转账回调地址由支付回调域名生成，固定路径：

`https://你的API域名/api/chef/transfers/notify`

该路径须公开可访问、保留原始请求体。转账结果经过 RSA 验签、APIv3 解密并核对商户、AppID、OpenID、商户单号、金额和微信转账单号。成功确认页面只是交互结果，不能代替实际到账；只有微信回调或查单终态为 SUCCESS 才显示到账。

小程序使用原生 `wx.requestMerchantTransfer`。旧微信客户端会提示升级；H5/网页显示收入但引导去小程序绑定与确认收款。厨师输入微信实名姓名并授权校验，数据库加密保存，发送微信时用微信公钥 RSA-OAEP 加密。

### 微信直接分账

需要额外开通普通商户分账权限，且**获批最大分账比例必须覆盖厨师应得比例**。例如平台佣金 15%，并不意味着商户天然有权向个人分账 85%。比例不足时系统会阻止付款或结算，不能仅改本地配置绕过微信限制。

```dotenv
WECHAT_PROFITSHARING_ENABLED=false
WECHAT_PROFITSHARING_MAX_RATIO=
```

只有权限和额度获批后才填入实际最大比例并开启。新订单将携带 `settle_info.profit_sharing=true`。厨师使用个人 OpenID 接收，关系为 PARTNER，提交其授权的实名信息。每笔支付对应持久化分账任务，重复查询/响应不重复记账；定金和尾款分别按分账额度分配，合计恰好等于厨师收入，平台剩余资金解冻。

当前直接分账不支持含平台优惠补贴的订单，付款前会提示取消优惠券；补贴订单应保持默认余额提现路径。分账前发生退款沿用微信原路退款，完成退款后仅按剩余资金结算。

## 财务操作

1. 财务人员先注册独立账号。
2. 平台管理员进入“财务权限”，按账号授予 FINANCE（财务专员）或 FINANCE_MANAGER（负责人），填写原因。不可授权本人，所有变更保留审计；本次没有自动给现有业务账号增加财务权限。
3. FINANCE 在“结算提现”查看订单保护期和净实收，点击“结算收入”。余额结算是产生应付厨师的余额，并不表示已转到微信零钱。
4. 厨师在小程序申请提现后，财务核对并审核通过，worker 才会向微信发起转账。审核人不能是该提现的申请人。
5. 厨师看到“待确认收款”后打开微信确认页。财务和厨师都能主动查询结果；worker 自动补查。失败确定后退回余额，可重新申请。
6. FINANCE_MANAGER 可以查看结算及提现、主动核对微信结果；现有售后工单审批仍沿用客服建议、负责人批准、财务执行的职责划分。

## 异常重试保护

- 微信查无此单、需要重新提交提现或分账时，再次检查数据库中的审批、厨师资格（提现）及售后状态。出现争议后暂停新的出款请求，冻结余额保留；已提交微信的请求仍继续查单核实结果。
- 超期提现转人工核查采用事务读取最新状态，避免覆盖并发到账回调。人工核查期间收到有效签名的最终结果，仍可按实际结果确认到账或释放冻结金额。
- 已结束的分账不会被较晚返回的处理中响应覆盖；分账结果同步写入订单结算信息。
- 已结束的提现可在支付通道未启用时读取本地结果。业务界面测试服务明确关闭支付、转账和分账开关，避免继承部署配置后误用真实渠道。

## 异常处理边界

- 微信直接分给个人 OpenID 的款项，不支持商户分账回退接口自动追回；已结算后发生售后需要财务核对、人工追偿。系统阻止直接重复退款/出款，不虚构追回成功。
- 分账部分失败会显示“需要处理”，保留原任务与已成功流水，不把整单记为已到账，不自动改成余额补发。运营需在商户平台处理后核对结果。
- 商家转账查询接口仅支持近期账单。本实现超过 29 天未确认的提现转为 REVIEW_REQUIRED，余额继续冻结，财务需核对微信资金账单，不能重新发送同一笔不明款项。自动下载账单对账、逾期人工核销和银行卡提现不在本次范围。
- 开通权限、商户资金余额、业务场景报备及真实收款账户必须由平台准备，不能以本地测试通过替代。
