## 2. 术语与对象

- **预约申请**：用户提交的服务需求，尚未形成已支付订单。
- **报价单**：来自套餐或厨师针对自定义需求提供的可支付费用明细，有版本号和失效时间；报价不等于支付后的正式接单。
- **软锁档**：自选厨师报价有效期内临时占用该厨师档期；报价失效即释放。匹配订单在选定厨师前不占用多位候选档期。
- **硬锁档**：自选厨师支付成功时锁定，平台匹配在抢单成功时锁定；取消、改期或履约结束后释放。
- **订单成立**：所选定金或全款支付成功且规则快照固化，生成待接单订单；不代表厨师已经接受服务。
- **服务性收入**：基础服务、买菜服务、清洁、加时、增项和固定交通服务费。
- **代垫费用**：食材、停车、过路等有凭证且事先约定的实报实销款。
- **服务完成确认**：用户现场确认，或从服务结束时间起默认 72h 自动确认；触发结算资格检查，确认不等于尾款到账。本文“履约完成”指同一事件。

| 对象 | 必须记录的关键字段 |
|---|---|
| 预约申请 | 用户、选厨模式、指定厨师或候选条件、地址区域、服务时段、人数、双食材模式、需求、创建/失效时间 |
| 报价单 | 版本、费用明细、有效期、规则版本、软锁档、提交人、用户确认记录 |
| 订单 | 报价/规则快照、首付款类型、定金比例、已收/已退金额、剩余应付、接单截止时间、绑定厨师、硬锁、服务结束与确认时间、七个状态域、保单关联、地址解锁记录 |
| 支付/退款/补款单 | 定金/全款/尾款/增项类型、关联订单/原支付单、单独的请求状态、渠道流水、幂等键、金额、失败原因、回调原文引用 |

## 3. 状态域与通用约束

以下七个状态域独立维护；“付款成功”“厨师接单”“完成确认”“费用结清”分别记录，不得相互替代。

| 状态域 | 正式状态 |
|---|---|
| 预约/合同 | 待支付、待接单、已接单、支付异常、已履约结束、已关闭、已取消 |
| 支付汇总 | 未支付、已支付（定金）、已支付（全款）、部分退款、全额退款 |
| 履约 | 不具备资格、待服务、已出发、已到达、服务中、待完成确认、已完成、服务中止、厨师爽约 |
| 费用 | 预估已确认、待最终确认、待补款、待退款、已结清、争议中 |
| 售后 | 未申请、处理中、待举证、已裁定、已关闭 |
| 结算 | 不具备资格、待用户确认、冻结、待结算、结算中、已结算、结算失败 |
| 评价 | 不可评价、可评价、已评价、已过期、已隐藏 |

支付汇总只反映已成功的资金事件；每笔定金、尾款、增项支付请求另有未发起/处理中/成功/失败/超时状态，退款请求另有待执行/处理中/成功/失败状态。尾款失败不得抹掉已收定金，退款失败不得从已收金额中减款。汇总为“已支付（全款）”也不自动代表最终费用结清。

### 3.1 合法状态转换矩阵

下表限定主要状态转换；同一事件可按前置条件驱动多个状态域。失败/超时请求须查明渠道结果再以幂等键重试，不得凭客户端回调推进状态。

| 状态域 | 合法转换（事件 → 前置条件 → 结果） |
|---|---|
| 预约/合同 | 待支付 → 所选首付款成功且报价有效、自选硬锁成功或匹配待指派 → 待接单；待支付 → 收款成功但报价失效/自选硬锁失败 → 支付异常；待支付 → 未收款且报价到期/用户撤回 → 已关闭；已关闭 → 迟到的收款成功 → 支付异常；待接单 → 自选接单或抢单原子绑定并锁档成功 → 已接单；待接单 → 拒单/自选5min超时/匹配N分钟流拍/用户取消 → 已取消并退款；已接单 → 取消或认定爽约 → 已取消；已接单 → 完成确认或部分履约中止且费用结清 → 已履约结束；支付异常 → 全部实收原路退款成功 → 已关闭。 |
| 支付汇总 | 未支付 → 所选首付款成功 → 已支付（定金）/已支付（全款）；已支付（定金） → 尾款足额到账 → 已支付（全款）；有实收状态 → 部分退款成功 → 部分退款；有实收状态 → 累计成功退款等于累计实收 → 全额退款；部分退款 → 合法增项/尾款到账 → 按实收与已退金额重新汇总。请求处理中或失败不改变汇总。 |
| 履约 | 不具备资格 → 厨师已接单、硬锁与认证有效 → 待服务；待服务 → 出发留证 → 已出发；已出发 → 到达签到 → 已到达；已到达 → 开始服务 → 服务中；服务中 → 提交完成凭证和结束时间 → 待完成确认；待完成确认 → 用户确认或结束起72h无争议自动确认 → 已完成；待服务/已出发/已到达/服务中 → 无法继续 → 服务中止；待服务/已出发/已到达 → 未开始履约且认定爽约 → 厨师爽约。 |
| 费用 | 预估已确认 → 提交最终明细 → 待最终确认；待最终确认 → 明细认可且净实收足额 → 已结清；待最终确认 → 含尾款的净实收不足 → 待补款；待补款 → 足额到账 → 已结清；预估已确认/待最终确认/待补款/已结清 → 取消或裁定有应退金额 → 待退款；待退款 → 应退全部成功且剩余义务结清 → 已结清；预估已确认/待最终确认/待补款/待退款/已结清 → 异议或凭证问题 → 争议中；争议中 → 裁定 → 待补款/待退款/已结清。 |
| 售后 | 未申请/已关闭 → 有效申请（包括待完成确认时） → 处理中；处理中 → 需补证 → 待举证；待举证 → 补齐或举证期限届满 → 处理中；处理中 → 裁定 → 已裁定；已裁定 → 资金动作完成且申诉期结束 → 已关闭。 |
| 结算 | 不具备资格 → 提交服务结束凭证 → 待用户确认；待用户确认 → 完成确认、费用结清且无售后 → 待结算；不具备资格 → 部分履约裁定、费用结清且无售后 → 待结算；待用户确认/待结算/结算失败/不具备资格 → 欠款、退款、争议或资金异常 → 冻结；冻结 → 异常解除且尚未完成确认 → 待用户确认；冻结 → 异常解除、履约与金额均符合资格 → 待结算；待结算 → 资格复核并提交渠道 → 结算中；结算中 → 渠道成功/确认失败 → 已结算/结算失败；结算失败 → 经核对重试 → 结算中。 |
| 评价 | 不可评价 → 服务完成确认 → 可评价；可评价 → 提交初评 → 已评价；可评价 → 确认起7天届满 → 已过期；已评价 → 确认起15天内提交追评 → 已评价；已评价 → 违规处置 → 已隐藏；已隐藏 → 申诉恢复 → 已评价。 |

跨域约束：

- 只有首付款成功、厨师接单、认证/区域/保险有效且硬锁成立才可开始履约；匹配订单未指派时履约始终为不具备资格。
- 服务确认与尾款分开：72h 到期不触发自动扣尾款；单纯欠尾款不延长完成确认和评价时钟，费用保留待补款、结算冻结。尾款期限及逾期处置见对齐记录 DTL-PAY-001。
- 有退款请求处理中/失败、待退款、争议或开放售后时，不得新发结算。已发渠道的结算遇到售后先登记冻结请求并查询渠道；确认未付才冻结/撤销，已付则保留已结算、建追偿流水，不能伪造渠道停止结果。
- 取消、流拍先终止接单资格并释放档期，退款单独异步处理；退款失败的已取消订单不得恢复接单。退款只退累计实收中尚未退回的金额，不得按订单总价退未收尾款。
- 支付成功但硬锁失败/报价失效：合同=支付异常、履约=不具备资格、费用=待退款、结算=冻结；幂等发起全部实收原路退款，全部成功后费用=已结清、合同=已关闭。失败保留支付异常及退款请求失败信息转人工。
- 同一订单的退款、结算、尾款回调与取消按服务端事件顺序及幂等键归并，迟到回调不能复活取消订单。全部实收退回且无待清义务时不得发起结算；已结算的历史记录不回退。

所有状态变化均写入事件记录：订单号、状态域、前后状态、操作者、时间、金额、规则版本、原因、凭证及幂等键。越权、非法前置条件、重复请求和终态回退拒绝并留痕。

## 4. 预约、报价、档期与支付

| ID | 触发与前置条件 | 状态/档期结果 | 时限与异常 |
|---|---|---|---|
| `TR-BOOK-001` | 用户确认报价并支付所选定金或全款。 | 合同=待接单；自选锁定指定厨师，匹配待抢单绑定。履约=不具备资格。 | 自选从进入待接单起5min内处理，拒单/超时取消并退全部已付款。 |
| `TR-QUOTE-001` | 套餐报价或厨师对自定义需求出价；完整列示费用与服务范围。 | 合同=待支付；自选报价软锁，匹配报价不占候选档期。报价不是正式接单。 | 沿用报价有效30min的补充默认值，后台版本可调；支付后不得单方改价。 |
| `TR-PAY-002` | 用户在有效报价内选择定金（默认30%）或全款。 | 实收成功后形成待接单订单；支付汇总为已支付（定金）或已支付（全款），记录待付余款。 | 自选硬锁失败/报价失效转支付异常；单次失败可在有效期内重试；尾款期限待发布。 |
| `TR-BOOK-002` | 支付成功后发现档期冲突、厨师材料失效、平台关闭服务区或其他无法安全履约情形。 | 立即冻结履约与结算并创建异常工单。用户书面同意改期时免费改期一次；否则由平台取消订单、全额原路退款、冲减全部佣金并释放硬锁档。 | 不得静默释放、强制改期或将此类风险转嫁给用户；厨师责任与补偿另按运营调查处理。 |

普通预约沿用最短提前24h、最远30天、服务前后各60min缓冲的补充默认值；急单不受24h最短提前限制，2h内需上门按急单路径处理，最小可承诺提前量见 DTL-MATCH-001。后台可按片区调整默认3km直线距离。所有路径仍须校验真实可用档期及交通缓冲；同一厨师重叠时段最多一个硬锁订单。

`TR-BOOK-003`（支付后接单与流拍）：自选从服务端进入待接单起5min内由指定厨师处理，拒单或超时自动取消、退回全部已付款；不能用通知发送失败延长计时。平台匹配从进入派单队列起按已发布的N分钟计时，按原文推荐3位候选（不足3位的处理/补推见 DTL-MATCH-001）。同一事务中完成“订单仍待接单、候选有权抢单、档期可用→唯一绑定厨师并硬锁”；失败方不能收到接单成功或拿到完整地址。流拍终止后原路退全部已付款，推送备选厨师并按活动规则发补偿券。并发抢单与超时只能有一个最终结果。

`TR-MATCH-001`（距离与急单）：普通订单仅向默认 3km 直线距离内、认证有效、接单开关开启且无冻结的厨师推荐；后台可按片区调整半径。服务开始前 2h 内的急单优先推送给 1km 内空闲厨师。匹配结果必须记录候选快照、距离、规则版本和推送结果。

`TR-COUPON-001`（基础优惠券）：优惠券必须保存适用片区、有效期、门槛、不可叠加和退款退券规则快照；核销、撤销、补偿券和退款不得使用当前活动规则重算历史订单。券后定金、平台/厨师分摊、佣金基数和退券金额在财务规则发布前不得由页面自行计算。

## 5. 费用、佣金与采购

| 费用项 | 用户支付方式 | 是否计佣 | 规则 |
|---|---|---:|---|
| 基础服务、买菜服务、清洁、加时、增项、固定交通服务费 | 报价预付或经确认补款 | 是 | 明确单价、单位、数量和服务边界。 |
| 食材采购费 | 预估预付，按实际多退少补 | 否 | 必须有有效小票或经仲裁认可的凭证。 |
| 停车、过路等代垫 | 约定预估或经确认补款 | 否 | 事先约定、凭证、逐项列示。 |
| 平台补贴/优惠券 | 依活动快照 | 见活动规则 | 基础优惠券属于V1；券后定金、分摊和退券见 TR-COUPON-001。 |

`TR-FEE-001`：订单应付=服务性费用+预计代垫−优惠，所选首付款与完整应付分开记录。实际采购比预估少先调减最终应付：已付全款时原路退差额，只有定金时先减少待付尾款，净实收仍高于最终应付才退款。超过预估需线上变更、用户确认并支付经确认的增量后方可支出；不得二次收取已到账尾款。沿用单笔预计采购费1,000元的补充审核上限；无有效小票转仲裁，未确认超额不得向用户默认追收。净实收=累计成功收款−累计成功退款；待补款=max(最终应付−净实收,0)，待退款=max(净实收−最终应付,0)。

`TR-COMMISSION-002`：无优惠场景，佣金=经确认的服务性收入×订单快照费率，按分四舍五入；厨师应得=经确认服务性收入−佣金+经确认代垫−已确认扣款。费率按厨师等级和业务类型配置，后续等级变更不重算历史订单。食材与代垫不计佣；退款同步冲减对应收入及佣金。优惠补贴及取消扣款的分配/计佣须按已发布活动和财务版本执行，详见 DTL-COUPON-001、DTL-COMMISSION-001；15%不是固定生产费率。

`TR-REFUND-AUTO-001`：规则可确定的退款（24h 前取消定金退款、临近取消规则、厨师/平台取消、采购预估差额、已支付无法履约的全额退款）可自动执行，但必须由财务负责人事先发布版本化的“自动退款授权”：明确适用规则版本、单笔/日累计上限、生效期、异常拦截条件和撤销人。系统以该授权作为审批事件，生成授权版本、规则版本、计算明细、渠道流水和执行结果；财务专员只处理授权外、失败、异常或超阈值退款。任何非规则退款、部分履约、结算后退款、人工改价退款仍依 `COMP-RBAC-002` 走客服建议→财务负责人审批→财务专员执行。

## 6. 最终费用、完成、售后与结算

1. 厨师上传成品菜照片、采购凭证与最终费用，记录真实服务结束时间 E；补传或改价不得重置 E。
2. 用户可现场确认完成，或从 E 起默认72h无异议自动确认（可配置并保存快照）。有缺失凭证或服务/费用争议时转工单，不能以自动确认认定争议已解决；单纯尾款未付不阻止无争议的完成确认。
3. 对最终费用逐项确认后，按 TR-FEE-001 比较净实收：不足为待补款（含尾款），超出为待退款，无差额为已结清；到账或退款失败不算结清。
4. 完成确认起7天内可初评，15天内可追评，与结算解耦；服务完成后7天内可发起普通售后，待完成确认阶段同样可提出异议和售后。
5. 手动/自动确认触发结算资格检查：费用已结清、无开放售后、无资金异常才进入待结算，按配置批次结算至厨师钱包。不再增加固定售后冻结期或固定T+3延迟；未收尾款时冻结结算，不能将确认事件当作已收款。
6. 结算在途遇到售后按第3.1节核对渠道；结算后退款新建追偿/赔付流水，不改写历史结算。

食品安全、人身安全、骚扰、欺诈等事件不受普通售后窗口限制，按 OPS-INCIDENT-001 处理。结算后赔付/追偿路径由 BLK-SETTLE-001 关闭。

`TR-FEE-002`（费用确认卡住）：禁止自动确认的条件（缺必要凭证、已申请售后、支付异常）出现时，费用=待最终确认并冻结结算，创建异常工单。厨师须在 24h 内补齐凭证；逾期未补、凭证仍无效或用户提出异议时，客服须在后续 24h 内将工单转为售后=待举证，并通知双方。待举证最长 72h；期满后仲裁员须基于已有订单、签到、聊天、照片和支付证据裁定确认、部分退款或全额退款，财务按 `TR-REFUND-AUTO-001` 或 `COMP-RBAC-002` 执行。凭证补齐且用户无异议后可由用户确认或客服在留痕后人工确认；确认前订单不得进入结算，也不得静默关闭。支付异常必须先由财务对齐渠道流水再继续。

`TR-STOP-001`（服务开始后中止与部分履约）：履约进入服务中后取消或中止，不适用第 7 节按时间档的服务费退款，按本条逐项计算实际已履约服务性收入。报价中的每一服务项必须选择以下一种计量方式并保存快照：

| 服务项 | 默认完成认定 | 实际已履约收入 |
|---|---|---:|
| 基础做饭服务 | 四阶段（沿用的部分履约计量补充）：备菜 20%、烹饪 50%、出餐/交接 20%、基础归位 10%；每阶段由签到、照片或双方确认佐证 | 套餐服务费 × 已完成阶段比例 |
| 买菜服务费、固定交通服务费 | 已完成采购/到达服务地址即 100%，否则 0% | 该服务项全额或 0 |
| 餐后清洁、单项增值服务 | 服务项完成即 100%，未完成 0% | 该服务项全额或 0 |
| 按小时加时 | 以已确认开始/结束时间计算，按分钟向下取整 | 单价 × 已确认分钟/60 |

责任在厨师（能力不足、擅自离场、重大迟到等）时，服务性收入不计收、取消未付服务义务并退回实收中的服务款，已确认代垫凭证另处；认定整单厨师取消/爽约则按 TR-CANCEL-002 全退已付款。用户要求中止或不可抗力时按上表和证据确定已履约收入；厨房设备故障、用户不在家优先按 TR-NOSHOW-001 专门规则，不直接套用阶段费。最终应付确定后按 TR-FEE-001 的净实收公式计算退款或待补款，避免定金订单产生负退款或退未收款；未发生/未获确认代垫取消收费，实收超过最终应付的部分原路退款。优惠订单另按活动快照分摊。

## 7. 取消、改期和爽约

`TR-CANCEL-001`：Δ=约定服务开始时间−取消请求服务器时间。原文已定定金默认占总金额30%、提前24h以上可退定金；本次将恰好24h暂归入可退档并记录于 DTL-CANCEL-001。待接单取消按原文待接单可取消口径退已付款；已接单且Δ≥24h退定金，Δ<24h扣除规则由后台发布。临近扣款比例、全款订单退款映射、已采购成本分摊及扣款计佣原文未给完整值，见 DTL-CANCEL-001，不再套用旧固定四档；下单前展示、支付时保存版本，缺少必要参数不得开启对应收费规则。任何退款不能超过净实收；用户不在家走 TR-NOSHOW-001。

| 取消时点（Δ） | 默认处理 | 已授权不可退代垫 |
|---|---|---|
| 已接单且Δ ≥ 24h | 定金全退；全款映射待发布 | 定金可退承诺不被自动代垫扣除覆盖，成本分摊待细化 |
| 已接单且Δ < 24h | 按已发布临近取消规则；金额/基数待定 | 按已发布规则与凭证分摊 |

`TR-CANCEL-002`：厨师取消/爽约、平台安全取消时退回全部已付款、取消未付尾款义务并冲减佣金；提供备选厨师、规则内补偿券并记录爽约调查及处罚。不可抗力下服务性费用原则全退，已授权且无法退回的实际代垫由客服依证据裁定。双方可发起改期协商，未经对方确认不得更改时间或菜品。

`TR-NOSHOW-001`：厨师到场发现用户不在家，须拍照留证、记录联系/等待并发起协商，按已发布规则扣部分上门服务费，不得默认扣全部加工费。上门后因厨房设备故障无法做饭，双方可协商改期或部分退款，不收取上门加工费，可酌收少量实际交通成本；适用范围、等待时间及交通费上限见 DTL-FEE-001，已采购食材单独按凭证协商。按 TR-FEE-001 计算净实收差额。

`TR-RESCHEDULE-001`：用户或厨师可发起时间/菜品变更，须另一方确认。时间变更在同一事务中校验新档期、缓冲、认证、区域和保险有效性，再锁新档期、释放旧档期；失败保留原单与原档期。仅改时间且不改费用时沿用原报价/佣金/取消规则快照；菜品/范围或费用变化需生成线上变更版本并由用户确认，正差额线上补款、负差额按净实收退款，不能单方涨价。拒绝改期不自动触发免费退款，正常取消按 TR-CANCEL-001；平台/厨师无法履约按 TR-BOOK-002、TR-CANCEL-002 全退。原文未规定免费改期次数，不再强加一次及提前24h限制。

## 8. 规则版本与计算示例

报价确认时冻结：报价版本、取消规则、佣金比例、服务边界、区域/档期规则和优惠规则。后台后续改动不得追溯重算已成立订单；即时安全停单可作用于存量订单，但须记录原因和人工处置。

以下金额单位为分；E1–E4、E8–E9为无优惠的计算样例，示例佣金率15%，不代表生产配置。E5–E7是参数待定的场景，不能当作已算出的验收金额。

| 示例 | 服务收入 | 实际代垫 | 用户支付总额 | 退款 | 用户净支付 | 佣金 | 厨师应得 | 说明 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| E1 正常 | 100000 | 30000 | 130000 | 0 | 130000 | 15000 | 115000 | 无退款。 |
| E2 食材少花 | 100000 | 26000 | 130000 | 4000 | 126000 | 15000 | 111000 | 预估 30000，退款 4000。 |
| E3 经确认超支 | 100000 | 35000 | 135000 | 0 | 135000 | 15000 | 120000 | 补款 5000 成功。 |
| E4 定金订单24h前取消 | 100000 | 0 | 30000 | 30000 | 0 | 0 | 0 | 定金按30%，提前24h以上全退。 |
| E5 定金订单临近取消 | 100000 | 0 | 30000 | 按规则 | 按规则 | 按规则 | 按规则 | 依后台发布的临近取消规则计算。 |

## 9. 人工干预与审计

客服可受理取消、售后和证据；不得无理由直接改变金额。财务负责执行已审批退款和结算；退款发起与执行需职责分离。超过后台金额阈值的退款、补款、负结算、规则变更须二人复核。所有人工处理必须引用订单、规则版本、证据和处理结论。具体权限见 `COMP-RBAC-*`，操作流程见 `OPS-FIN-*`。
